Research Agents Review

A code-level account of the Research Tool's multi-agent research flow. It follows one campaign from the person's request to the lock, and ends with a design for a better test and eval harness. It is written for the engineer who will review the flow and build that harness.

Code: the task/clan-fields worktree at /home/batunii/Documents/Code/napkin-os-wt/clan-fields, HEAD cf4e45b, read on 2026-09-28. Paths are relative to the worktree root unless marked otherwise. References are file:line. The worktree had uncommitted edits while this was written, in server/napkin/pipeline/synthesise.py, handlers/synthesise_findings.py (a redo: audience input), campaign-research/index.html (+15 lines), pipeline.yaml (+1 line) and app/src/shell/decisions/*. For synthesise.py this document cites HEAD. For index.html it cites the working copy, which can be up to 15 lines off HEAD. Contract sections are cited as middleware-api §8.4, campaign-clan §11 and so on. Nothing here changes code.

Summary

  • Shape. A campaign is one middleware job, start_campaign, with six stages in order: extract, identify, select, research, synthesise, report. Layout runs inside report. The job holds each stage's output as a cached "chunk" and hands the host every chunk not yet in the document's decision chain, on every poll. The host applies each change, rebuilds the projection and returns the document. A person then reviews through host routes and locks.
  • Model versus code. Every model call is structured output validated against a JSON schema and retried once. After each call, deterministic code decides what is written: verbatim-quote checks, figure-in-quote checks, the cite rule, the merge and contest rule, the layout rule, and derived confidence. The model's own confidence is never read.
  • Cost. Model calls per campaign are 6 + S logical calls, where S is the number of lens×market units that got at least one source. A few more happen when a person types a category the tree does not know. Research calls are R ≤ 8 × markets. In the latest real run (2026-09-28, 15:41–15:54 UTC) the whole job took about 13 minutes. Research was about 3 of them. Layout took 5.7: its call timed out at the mock's 180 s and the SDK retried it.
  • Testing today. Coverage is broad and fast (126 pytest tests in the working tree, about 10 s, plus a contract suite and Rust host tests). All of it runs on hand-written fakes. Nothing replays a recorded real run. Nothing evaluates research quality, layout quality or timing. There is no browser end-to-end test of the review flow.
  • Bugs found. See §4.3; numbers 1, 4, 5 and 7 have been fixed since. The ones to look at first:
    • Layer decisions for the merge and for contests are stored with an empty rationale. I confirmed this in the dev layer DB.
    • The cite rule drops claims that mention years, or money written as €1.5m.
    • A refused stage leaves the job waiting at report forever. That blocks both a new campaign and Refresh report on the document.
    • The layout rule accepts <clan-field ref="gap_…">, which crashes the view's renderer.
    • The reviewer source written by /verify never reaches shared/sources.yaml.
    • A host-opened stale-write contest cannot be resolved, so it blocks the lock forever.

1.5 The reply and the change

Every reply to start_campaign, job_status and answer_question is the §2 envelope, with task: start_campaign (app.py:102-105, middleware-api §8.2):

{ api: "napkin.middleware/1", task: "start_campaign", handler: "start_campaign@1.0",
  job:    { id, state, stage, progress: {done, total: 6}, question | null, started_at, finished_at, error },
  result: { summary, messages: [{id, text, stage}] },
  change: { doc, base_version, read, data_patch, facts_append, findings_append, sources_append, decisions } | null,
  trace:  { scope, backend, model, hits, usage: {input_tokens, output_tokens} } }
  • Chunks. Each stage calls add_chunk (campaign.py:177-215) once. The chunk holds the patch, the read-set, the facts, findings, sources and decisions, and the agent message. Each field the patch writes is added to the first decision's targets when no decision names it (:204-207).
  • What a reply carries. reply_change (:278-290) sends every chunk whose decision ids are not all in known_ids(clan) (doc.py:134-141). known_ids includes decisions a host contest withheld. combine (:106-119) merges the chunks: base_version is the earliest chunk's, and read holds each path's earliest reader. After done, a poll with nothing pending gets the last change again.
  • Working copy. sync (:152-168) rebuilds the job's working copy W from the request's clan, plus chunks that have not landed yet, plus the person's answers not yet written (d_PENDINGANSWER). Later stages read W. The report stage instead reads latest_clan, the document the host last sent.
  • Decisions. Each one comes from doc.decision() (doc.py:230). Reasoning follows reasoning.py: decided, because[] with cites, rejected[] or only_option, certainty (always derived), would_change_if, and optional attention. make() raises on a malformed shape (reasoning.py:92-103).

1.6 The host applies it: settle, projection

The host findings in 1.6, 1.8, 3.5, 4 and 5.4 come from a delegated read of the Rust sources. I spot-checked them but did not re-read every line.

  1. Proxy. api_proxy (proxy.rs:106) splices attachment text and images from the .extracted/ sidecar into the payload (read.rs:234-321). It then sends {request_kind, payload, clan}. clan is clan_context_for_agent (read.rs:334-364), which carries the whole data (projection included), the whole chain, and facts, findings and pipeline. It does not carry the sources member. It does not apply any classify marks. The HTTP client has no timeout (proxy.rs:32).
  2. Settle. Session::settle_middleware (session.rs:499-550):
    • checks api;
    • runs middleware::apply (ops/middleware.rs:137);
    • replaces data.change with the outcome;
    • when the change landed, attaches clan = document_now() and emits DataChanged.
    A refusal is {applied:false, reason} under ok:true. It is never an HTTP error.
  3. Plan (ops/middleware.rs:153-349):
    • change.doc must match the document.
    • No projection key is allowed in the patch.
    • Every decision's reasoning is checked. The floor is pin, contest, finding, verdict, and any edit whose action is propose. The app adds the edits under campaign, selection and report (pipeline.yaml reasoning.edits). A missing or malformed reasoning refuses the whole change.
    • Host-owned fields (actor, scope, handler, backend, timestamp) are overwritten. The sent values are kept as claimed_*.
    • If the base is stale and there is no read-set, the change is refused ("rerun").
    • If the base is stale and a read-set exists, each key applies if nobody changed it since. Otherwise the host opens a host contest (kind: contest, chain-only) and withholds the job's decision.
    • facts_append and findings_append are deduplicated by id. The same id with different content refuses the change.
    • sources_append keeps the first record for an id.
    • An exact repeat is "already applied".
  4. Assemble (ops/assemble.rs:77):
    • writes shared/facts.yaml, findings.yaml and sources.yaml;
    • rebuilds data.projection from the exact member bytes (ops/members.rs:217-315: built_from.{facts,findings,sources}_sha256, pins[id] with stale, quotes and replaced_by, findings[id], sources[id]);
    • validates against the schema;
    • prepends the decisions to agent/decision-chain.yaml.
    The store does not check Change::base (W2-A4, store.rs:173-185). Within one process, the view mutex serialises writes.

2. Each agent

Tags: model marks a model call. code marks a deterministic step. Every model call goes through ModelPort.call (model.py:313-369). It validates the output against the schema, retries once with the validation error fed back, and otherwise raises ModelError(invalid_output). Handlers never see the wire.

2.1 Extract ("Read the ask")

Reads
The prompt and each attachment's host-extracted text, as materials with ids (doc.build_materials, doc.py:269). Also the subject brand's roster pins, if the document already holds them.
Deterministic first
code roster_proposals (extract.py:244-261): roster pins give categories and client_org as proposed. In start_campaign these fields are skipped, because identify owns them (campaign.py:404-407).
Model call
model extract, SYSTEM (extract.py:30), SCHEMA (:52-72), max_tokens 8000 (:284-288). Every value comes back with {quote, material_id}, plus grounds.
Checked in code
verify() (extract.py:110-205):
  • Quote check: the quote must be found in the material by find_quote (rules/quotes.py:38-59). It tries an exact match first, then one folded for whitespace and typographic quote marks. It ignores case only when the quote is 12 characters or more. The stored quote is the material's own substring. A quote that fails drops the value, with a note.
  • Markets: ISO 3166-1 alpha-2 only (rules/markets.py:24).
  • Budget: reduced to a band and never stored as a figure; the span keeps no quote. A non-EUR amount within ±15% of a band edge abstains (rules/budget.py:20-30).
  • in_market: explicit YYYY-MM-DD dates whose year appears in the quote.
  • Competitors: the subject brand is removed.
  • Human-owned fields are never written (doc.human_owned, doc.py:144-157): origin confirmed or stated, or an unanswered bad verdict.
Writes
campaign.* envelopes, origin: extracted, each with a source span or per-item item_provenance. Re-extracted lists are merged (merge_list_field, :212-241). New materials are written with licence client-confidential.
Decisions
One edit, action extract, carrying material_read and abstained. Its reasoning comes from extract_reasoning (:366-413): the model's grounds, cite-checked against the material ids. Certainty is high when every value verified. It is medium when the rules dropped any value, low when nothing was written, and is capped by the lowest roster pin. attention lists what was dropped.
Person afterwards
Confirm the extracted fields in report.confirm (brand, categories, markets, competitor_set first; report.py:259-282).

2.2 Identify (Extract's second job)

Reads
The materials and the category tree (layers.leaves()). Also the brand layer's roster row for the subject brand, and the person's earlier answers (self.answers, pending_text).
Model calls
model identify (campaign.py:364-399), max_tokens 4000. It returns brands with quote, basis (brand_label|named_as_ours|none) and a comparator flag, the client organisation, and at most two category leaves (enum = tree codes). It is cached for the job: re-running identify after an answer makes no second call. model classify_category, max_tokens 500 (:596-599), runs only when typed text matches no leaf via layers.find.
Checked in code
code
  • Every brand, client and category needs a verified span (_span, :350-362). As a fallback, the brand's name is matched as a whole word in the material.
  • decide_subject (rules/identify.py:44-71). A claimed basis counts only when the verified quote carries its cue and names the brand (checked_basis, :31-41). If exactly one claimed, non-comparator brand remains, it is the subject. If exactly one brand is named and it is not a comparator, it is the subject at certainty medium. Anything else asks.
  • Categories come from roster pins as proposed. Without a roster row the job asks, with ranked options plus "both" plus "Something else" (category_options, :74-90).
  • With no markets the job asks for free text. Free text is resolved by markets.from_text (rules/markets.py:31) and asked again as options.
  • A subject brand listed among the comparators is removed from competitor_set (:667-688).
Writes
campaign.brand (extracted), client_org (extracted or proposed), categories (proposed, citing the roster pins), and the roster pins themselves. When a person confirms the categories, it writes the brand layer's roster with a reviewer-verified source for that person (:617-627). That is a write to shared knowledge from a chat answer.
Decisions
  • edit identify, with reasoning from identify_reasoning (:707-725). Certainty is high for a label or an "ours" cue, medium for the only brand named. The roster pins' derived levels also feed it.
  • pin lookup for the roster row (deterministic).
  • edit identify for each question. It is always certainty low, with attention "Waiting for your answer".
Person afterwards
Answer the question (buttons or text). Then confirm the brand if its certainty was medium (the attention note).

2.3 Judge (select)

Reads
The prompt text only, plus the markets, the categories (with their regulated flag) and the eight lenses with their standing questions (research.py:39-56).
Model call
model select, SELECT_SYSTEM (campaign.py:57), SELECT_SCHEMA (:86-89), max_tokens 2000. The prompt tells it: "Research everything by default".
Checked in code
code (:742-757):
  • A skip without a reason is ignored, so the lens runs.
  • A per-market skip counts only when the market is in the campaign and there is more than one market.
In select_reasoning (:783-816), certainty is high when there is no skip or every skip's reason quotes the prompt (find_quote). It is medium, with attention, when any skip is the model's inference.
Writes
selection.lenses_skipped ({lens, market?, reason, decision}). The chosen pairs live only in the job's memory (self.selected).
Person afterwards
Check any inferred skip. "Research a skipped lens…" in the decision panel re-runs one through research_lens.

2.4 The lens researchers (one unit per lens × market)

Reads
The subject, the comparators, up to two categories, the lens's standing question and wanted keys, and the layers' existing facts.
Step 0: reuse code
For each entity (the category leaves, the subject, the comparators), layers.facts(layer, entity, key_prefix=lens ns, market) is checked. If any active row was retrieved within NAPKIN_REUSE_DAYS (30), the unit is served from the layer and makes no research or model call (research.py:157-167). One fresh row is enough to skip new research for the whole unit.
Step 1: research
caps.research.search(query, lens, market, entity, category=cats[0]) (:175-181). Only the first category is sent as the parameter, though the query text names both. The port (research.py:36-78) keeps http(s) sources that have non-empty excerpts. It raises ResearchError on a non-200, a timeout or a malformed body.
Step 2: tier code
tier_for(url) (rules/tiering.py:75-86) works from the URL alone. Primary means government or statistics domains or filing paths; secondary means a trade-press list; everything else is tertiary. Each source is recorded in the layer (add_source).
Step 3: model call
model extract_facts, SYSTEM (research.py:60-71), facts_schema (:78-95; enums for about, category, competitor and unit), max_tokens 8000. The payload holds the sources with verbatim excerpts. Each fact returns evidence[{source_id, quote}] and not_found[].
Checked in code
_check (:239-307):
  • The entity must be one this run may write about. The key is <lens namespace>.<suffix> and must match the key pattern.
  • A proportion must be between 0 and 1. A numeric unit needs a number.
  • Verbatim: the evidence quote is found in one of that source's excerpts (verbatim).
  • Figure rule: quote_supports (rules/figures.py:72-92). "A numeric fact must have its number in the quote it came from (to 1%, after percentages and k/m/bn multipliers); a date its year."
  • Evidence that fails is skipped. A fact with no surviving evidence is dropped.
  • as_of falls back to the earliest published_at, then to retrieved_at. A fact dated after it was learned is dropped.
Wanted keys the model says it did not find become gaps. A unit whose model call or research call failed becomes a gap carrying the error (:178-181, :212-216).
Writes
Candidates only. Nothing is pinned per unit; see the merge.
Decisions
One edit research_run per unit (:398-406). Its reasoning is written whole by code (run_reasoning, :543-589). Certainty comes from coverage: filled is high, thin is medium, empty is low. A failure gets attention.

2.5 The merge (deterministic)

Rule
code merge_rules.merge (rules/merge.py:39-80, campaign-clan §8). The identity of a fact is entity + key + market.
  • Same identity, same value: one pin, with sources unioned (that is the corroboration).
  • Same entity and key in another market: two facts, not a conflict.
  • Same identity, different values: a contest, open, with nothing picked.
  • A value that differs from a pin the document already holds: a contest against that pin.
  • Keys with an open contest are skipped.
Writes (D1)
Each merged pin is appended to the layer first, with the merge decision, and is then pinned from the row the layer returns (research.py:345-355). Contest values are appended with status contested. A frozen pin for each value is carried in the contest so that /resolve needs no layer call (:356-383). The selection.* patch covers runs, coverage per market and merged (merge_coverage, rules/confidence.py:48-55), gaps, contests, and lenses_skipped entries that a later run removes. sources_append holds the records for every src id a new pin or contest value cites (_source_records, :459-483).
Derived confidence
fact_confidence (rules/confidence.py:21-30):
  • Start from the best source's tier: primary gives medium; secondary or tertiary gives low; reviewer-verified gives high.
  • Add one level per independent registrable domain beyond the first, at most two, capped at high.
  • A fact resting only on tertiary sources is capped at medium.
Decisions
One pin research_merge. Its certainty is the lowest pin confidence (merge_reasoning, :592-621). Each contest gets a contest open_contest decision with certainty high ("which is right is what is open") and attention.
Person afterwards
Resolve each contest with /resolve and a reason; the lock waits for it. Low-confidence pins are listed in the merge's attention.

2.6 Synthesis

Reads
Pins only, never the raw layer: usable_pins, i.e. f_ ids that are not excluded and carry a valid confidence.
Model call
model synthesise (synthesise.py:86 at HEAD), max_tokens 6000. The schema restricts cites to the pin ids. The model proposes at most one finding per lens, and optionally an audience whose statements hold no figures.
Checked in code
code
  • Cite rule: clean_claim (rules/cite.py:14-25). The claim must cite at least one real pin and state "no figure absent from what it cites". The allowed forms are repr(v) and f"{v:g}", and for a proportion v*100:g and round(v*100) (figures.py:19-28).
  • The lens is corrected to one of the cited pins' lenses.
  • A cite set that is already written up is skipped.
  • The audience may contain no digits at all (_no_figures).
  • Confidence is derived by finding_confidence (confidence.py:33-37): the lowest cited pin, one level lower for a single or stale citation.
Writes
Findings with status: proposed and method: synthesis. campaign.audience, origin: proposed, only when no person owns it and it is empty.
Decisions
A finding synthesise_finding per finding, and an edit propose_audience. The reasoning is the model's grounds, cite-checked, with certainty equal to the derived confidence.
Person afterwards
Verify or reject every finding (lock blocker 3). Confirm the audience.

2.7 Drafter (report)

Reads
latest_clan: the document as the host holds it, once every earlier decision has landed (campaign.py:235-239, middleware-api §8.4). Pins must match f_[0-9A-Z]{6,}. Findings must be proposed or verified.
Model call
model report (report.py:112-113), max_tokens 6000, with the cite ids as an enum. It runs only if some lens has pins or findings. A failure is caught, and the prose then falls back to lines built in code (:114-117).
Checked in code
code clean_claim is applied to the headline, each summary line and each section claim (:118-132). A claim that fails is dropped. A missing headline or summary is replaced by a figure-free line built in code (:173-188). The structure is built in code, not by the model: the sections per lens, the pins, finding, contest and gap blocks, confirm, not_researched and based_on (:137-192).
Writes
report, replaced whole.
Decisions
One edit report. In report_reasoning (:209-247), certainty is the lowest confidence of what the headline and summary cite, one lower when the cite rule dropped any claim. Attention covers open contests, lenses not researched, and dropped claims. The dropped claims themselves appear only in the middleware log (:203-204), not in the document.

2.8 Layout

Reads
The structured report just built, plus the pins (label, value, unit, market, as_of, has_quote), the non-rejected findings, the open contests and the gaps (layout.py:62-80).
Model call
model layout, SYSTEM (layout.py:22-46), schema {html: string}, max_tokens 8000 (:83). It is the longest call in a run: 160–180 s on the mock.
Checked in code
code rules/layout.check (rules/layout.py:138-194):
  • Vocabulary: only the allowed tags and attributes survive. class keeps only cl-* and compact. A disallowed element is dropped with everything inside it.
  • Refs: each ref or refs must name a pin, a live finding, a contest or a gap. A chart may name only pins with a number (_check_clan, :197-223).
  • Evidence: each p, li, blockquote and figcaption must contain a clan-* element.
  • Figures: a block's own text may state no figure outside what its refs hold. Years are exempt (YEAR). Headings and cells are held to the same figure rule.
Acceptance (layout.py:87) requires fields + charts >= 3 and blocks >= 1. Otherwise, or on any model exception, the layout is built() from the structured report (:94, :98-139) and layout_by: built. Prompt rules that the code does not check: "say each thing once", "a figure at most twice", and "end with <clan-sources>".
Render side
The view sanitises again in ClanFields.layout (clan-fields.html:652-673). An unresolved ref renders as <span class="clf-missing">.
Person afterwards
Nothing specific. The tray lists what needs a person whatever the layout shows (clan-fields.md §1).

2.9 Verify (after review)

verify_finding (handlers/verify_finding.py:28-87) is a short task that only the host's /verify calls. It checks that the finding is proposed and that its cites are pinned. It then adds a human:<id> source at tier reviewer-verified and appends the finding's statement as a fact, method: synthesis. The fact takes the strictest licence of the pins it rests on and goes to the brand layer if any cited pin is there. The decision id is the host's. The reply's change is null, and result.pin and result.source go back to the host.

3.4 The job and poll model

  • start_campaign returns right away with queued or running (app.py:153-163). Only one unfinished campaign may exist per document; a second gets 409 job_state. compose_report is refused the same way while one is unfinished (app.py:178-180).
  • Polls are job_status, served by reply_change(clan). Each poll also moves the job's latest_clan forward, which is what releases the report stage. So the report stage runs only if the view keeps polling. Close the tab before report and the job waits in running until the document is opened again (resumeJob polls once).
  • Concurrency is bounded by process-wide semaphores: research 4 and model 6 (app.py:68-69). The research fan-out also uses a pool of research_concurrency threads (research.py:320-329). Units finish in submission order, so progress is reported in order.
  • progress counts stages (total: 6). The research fan-out is narrated in messages, not counted in progress.

3.5 The agent quota (web layer)

crates/napkin-web/src/meter.rs:

  • It is per tenant: an anonymous session cookie.
  • It counts calls, not tokens.
  • It lives in memory and resets on restart. There is no time window.
  • The cap is NAPKIN_AGENT_CAP, default 40 (main.rs:63-65). The dev stack sets 400.
  • charged() exempts only middleware job_status; malformed bodies are charged.
  • It is enforced before dispatch on /api-proxy (sandbox.rs:67-80). Over the cap the reply is HTTP 429, "agent quota reached for this session (used/cap)".

The quota is a count of submissions, not a cost control. A 3-market campaign costs the same one unit as a 1-market one. The module notes "a draft is roughly $0.30–0.40" (meter.rs:7), which is far below the observed $3.77 in research calls alone for the IBM job.

  2. confirmed The cite rule drops legitimate claims. unsourced_figures treats every digit run as a figure (figures.py:16, :43-45), and a pin allows only repr and :g forms. I ran the rule in-process:
    • "worth €1.5m" (pin 1500000) was dropped: 1.5 is not allowed, and :g gives 1.5e+06.
    • "€1,500,000" was dropped as 1,500 and 000.
    • "continues to 2030" was dropped: years are figures here, though the layout rule exempts them (rules/layout.py:38).

  3. likely A refused stage deadlocks the document. The report stage loops on cond.wait(30) until the host's chain holds every earlier chunk's decisions (campaign.py:235-239). A change the host refuses never gets there. This includes a missing reasoning, a stale base without a read-set, and an id with different content. The job then stays running for ever, so start_campaign and compose_report on that document are both 409 until the middleware restarts (app.py:154-156, :178-180). This contradicts §8.4 (4.2).
  4. likely The layout rule accepts refs the renderer crashes on.
    • _check_clan accepts <clan-field ref="gap_…">, because known() includes gaps (rules/layout.py:149-150, :216-218).
    • In the view, stateOf returns 'sourced' for a gap or src_ ref (clan-fields.html:295). renderField then reads pins()[ref], which is undefined, and throws (:343-345).
    • The throw escapes refresh()'s loop, so every element after it on the page is left unrendered.
  5. confirmed The reviewer source is missing from shared/sources.yaml. verify_finding returns result.source, a new src_ id, and the pin cites it (verify_finding.py:59, :76). The host pins the fact but does not add a source record. In the example document, the verified pin cites one src_ id that is absent from the sources member, so the drawer shows "pinned before sources travelled" for a pin made today.
  6. likely A host stale-write contest can never be cleared. The host opens chain-only contest decisions on doc#campaign.X (ops/middleware.rs:678-719). The decision view clears them only on a later resolve naming the target (decisions.rs:662-694). /resolve accepts only selection.contested[id] (review.rs:444-453). So /approve is 409 for ever.
  7. likely, not run Dialogs may submit twice. openDialog adds a click handler on each submit button that calls form.onsubmit (index.html:1457-1460). freshForm adds a form-level click listener that dispatches a synthetic submit (:1436-1443). Neither stops propagation. One click would therefore make two /verdict, /classify, /approve or patchData calls. Confirm it by counting host calls in a browser.
  8. risk The lock is enforced only by the review routes. middleware::apply and patch_data do not check it, so a job still polling after lock can write into a locked version.
  9. risk Repeated appends after review are refused. After done, any poll (for example resumeJob on open) resends the last change. If that change still carries a finding the person has since verified or rejected, the host refuses it as "different content". This is harmless but noisy: the jobs card shows "not applied". It becomes harmful only if a new chunk is ever bundled with a stale repeat.
  10. minor Layer writes happen before the checks that may discard them. _write appends each merged pin before checking excluded, already pinned and superseded (research.py:348-353). It also appends contested rows before discarding a contest whose values collapse to one (:368-376). This can leave contested rows in the layer with a decision the document never records.
  11. minor Unit-level reuse is all or nothing. A single fresh row for any entity skips new research for the whole unit (research.py:161-167).
  12. minor The dev stack may not run this worktree. ../stack/start.sh defaults W to the characters worktree, and the web log shows the shell served from clan-fields/app/dist. Check W before trusting a run as evidence for this branch.

6.3 P0: recorded and replayable fixtures (cassettes)

  • Where to tap. At the port boundary, which already takes test doubles:
    • the model client (Middleware(model_client=…), app.py:44-53; anything with messages.create, like FakeModel);
    • the research port (research_port=, with the search(...) signature FakeResearch has).
    Add CassetteModel(mode=record|replay|strict) and CassetteResearch. The Rust host and the view need no change.
  • Key. purpose + sha256 of the canonical payload + sha256 of the schema + model id.
    • Payloads carry volatile ids: layer-minted f_ and src_ ids, job-seeded decision ids, and as_of falling back to today.
    • Canonicalise before hashing: replace each id by <kind>#<order of first appearance>, and freeze today() and iso() (patch napkin.util).
    • Store the mapping, so the replayed output's ids are rewritten back into the current run's ids.
    • For extract_facts, also key on (lens, market) as a human-readable secondary key.
  • Contents. The request (payload, schema hash, model), every wire attempt (text, stop reason, usage, latency) including the failed ones, and the final object. For research: the request body and the response, including empty ones, with their latency.
  • Replay modes.
    • strict, for CI: a miss is a test failure naming the purpose and the diff of the canonical payload.
    • lenient, for prompt work: a miss falls through to a live call and is recorded.
    • timed: sleep the recorded latency, scaled, for timing tests.
  • Recording source. Run each scenario through the dev stack with MOCK_NO_CACHE=1, or against the real ports. The mock's research cache (<MOCK_DATA>/cache/research) can seed research cassettes, but drop its empty entries or tag them as such.
  • Confidentiality. Cassettes hold prompts and attachment text. Build the scenario corpus from synthetic or owner-approved briefs only. Never record client documents. Keep the store out of the repo if in doubt. The mock already refuses to dump bodies unless MOCK_DUMP_REQUEST_BODIES_TO is set (common.py:92-94).
  • Layers. Use FakeLayersService (tests/fake_layers.py), seeded per scenario (roster rows, pre-existing facts for reuse cases). Check that its ids are deterministic under a frozen clock. If they are not, the canonicalisation above covers them.

6.6 P1: quality evals

  • Research, per pin (LLM as judge, run on the replayed output). Give the judge the pin (entity, key, value, unit, market, as_of) and the source excerpts from the cassette. Score 0–2 on each of:
    • supported: the excerpt states it;
    • key fits the lens;
    • market-correct;
    • entity-correct: category, subject or comparator;
    • period-correct: as_of.
    Aggregate per lens. Also report the corroboration rate (the share of pins with 2 or more domains; 0% in the example document), the tier mix, and gaps per unit.
  • Findings. Score each: follows from the cited pins; states nothing beyond them; useful to a planner; compares markets when it could.
  • Report and layout. Score:
    • the headline is specific and supported;
    • nothing is said twice;
    • big numbers are the right ones;
    • the charts compare like with like;
    • open items are visible.
    Also compute in code: duplicate sentences, figures shown more than twice, the fraction of pins shown, the count of dropped claims, and layout_by.
  • Judge hygiene. Use a fixed rubric prompt and a pinned model. Run it on replayed documents so scores are comparable across commits. Calibrate it against the human sheet on 30–50 items before trusting it, and report the agreement.
  • Human spot-check sheet. Each week, sample 20 pins, 5 findings and 1 layout per scenario. For each pin, show the value, the quote with the figure highlighted, and the source link. The reviewer marks correct, wrong or unsure and a reason code. The results feed the judge's calibration and the golden updates. The OS drawer already shows this view, so the sheet can be a filtered list of drawer links.

6.7 P1: timing and load

  • A budget test per scenario. Replay with timed cassettes at 0.1× latency. Assert the wall time stays under a budget derived from the recorded run, and the logical model calls stay at or under 6 + S + k. Fail when the layout call or its retry dominates.
  • An aligned-timeouts test. Assert MOCK_TIMEOUT_MODEL is at least the middleware's per-attempt timeout for the layout purpose, or give layout its own shorter budget and a single attempt.
  • Load. Run 5 campaigns at once against the stack with timed cassettes. Watch the model semaphore (6), the research semaphore (4) and the mock's shared 4 slots. Record the queue waits: attribution is already logged per call (capabilities.py:76-82, model.py:338-339).
  • Poll behaviour. Count job_status requests per campaign in the view's e2e. The truncated mw.log held 357 job_status lines for about an hour spanning three jobs.

6.8 P1: browser e2e for the review flow

Run the real app in the real shell frame (sandbox="allow-scripts allow-popups"), against napkin-web and a middleware on cassettes. The harness's unsandboxed page cannot catch sandbox bugs. Outline (Playwright):

  1. Start the stack: mock layers only (MOCK_FAKES=layers), the middleware with cassette model and research, and napkin-web with a temp data dir. Create a Research Tool document from the seeded template.
  2. In the app frame (page.frameLocator('iframe')), type the S2 prompt and press Send. Assert body.working, and that the stepper advances.
  3. When the question card appears, click an option. Assert exactly one answer_question request and one human patchData, by intercepting /api-proxy and patch routes.
  4. Wait for body.done. Assert #rep-layout is mounted, no element has clf-missing, and nothing on console.error (a TypeError from bug 4 would show here).
  5. Open a pin and click "Looks right". Assert one /verdict; two would be bug 7.
  6. Open a finding and click Verify. Assert /verify, then the pin appears. Assert its source card is not "pinned before sources travelled"; that would be bug 5.
  7. Reject the other finding with a reason. Open the S6 contest, pick a value, give a reason, and resolve it.
  8. Assert the tray is empty, then click Lock report. Assert /approve returns 200 and the drawer offers no actions afterwards.
  9. In every dialog, press Enter in an input and assert the handler runs once. This tests the no-allow-forms workaround. Assert no "Blocked form submission" console message.
  10. Export the .clan and run the invariant checker on it.

Update the harness's inlined copy of clan-fields from app/templates/shared/clan-fields.html as part of its build, so it cannot drift again.
